# 014. Quality Gap Analysis: smollm2.c vs Ollama

**Document Type:** Cross-Reference Analysis
**Purpose:** Identify root causes of poor quality output
**Date:** 2026-05-28
**Status:** ACTIVE

---

## Executive Summary

This document synthesizes findings from 11 analysis documents to identify why smollm2.c produces suboptimal output compared to Ollama. The primary root cause is **numerical precision degradation** in the fast matmul path combined with **overly aggressive repetition penalty** that blocks valid tokens. Secondary issues include temperature inconsistency and tokenizer alignment concerns.

**Key Finding:** The model IS producing coherent tokens (".", "Ġto", "Ġin", "Ġand"), but the garbled output pattern ("*** *** ******* #") indicates the logits distribution is distorted - likely due to accumulated float precision errors.

## Section 1: Hidden State Flow Analysis

### Question: Is the current prefill correctly propagating hidden states?

**Answer: YES - The implementation is correct for transformer inference.**

From `sm2_context.c` lines 388-407:

```c
for (int t = 0; t < n_tokens; t++) {
    int seq_pos = t;
    
    // Get embedding for current token into scratch.x
    embedding_lookup(ctx->scratch.x, tokens[t], model->tok_embeddings);
    
    // Run this token through all layers
    for (int layer = 0; layer < model->n_layers; layer++) {
        layer_forward(ctx->scratch.xb, ctx->scratch.x, layer, model, ctx, seq_pos);
        // Swap buffers
        float* tmp = ctx->scratch.x;
        ctx->scratch.x = ctx->scratch.xb;
        ctx->scratch.xb = tmp;
    }
    
    ctx->scratch.kv_cache_len = t + 1;
    ctx->last_token = tokens[t];
}
```

### Why This Is Correct

For input "hello" (tokens [BOS=1, 28120]):
1. **Token 0 (BOS)**: Embed -> Layer0..29 -> KV_cache[0], output to scratch.x
2. **Token 1 (28120="hello")**: Embed -> Layer0..29 with attention seeing KV_cache[0] -> KV_cache[1], final hidden in scratch.x

This is the standard **autoregressive prefill** pattern. Each token:
- Goes through all 30 layers independently
- Stores K/V to cache during processing
- Attention sees previous tokens via KV cache

### The "Token Isolation" Finding Is NOT A Bug

Document 005 describes this as a potential issue, but the trace analysis confirms this is the **correct** behavior. The confusion arises from misunderstanding how transformers work:

- Tokens are processed sequentially to populate the KV cache
- Each token's hidden state depends on ALL previous tokens through attention
- There's no "hidden state propagation" between tokens in the same forward pass

**Verification:** `check_layer_trace` output shows:
- Layer 0 hidden state changes dramatically (magnitude 122 -> 71 -> 21)
- Layer 29 hidden state has high quality (range [6, 27])
- Logits show proper separation (top 27.59, 2nd 27.34)

## Section 2: Sampling Quality Issues

### Issue 2.1: Hard Block Is Too Aggressive (HIGH Priority)

From `sm2_sampling.c` lines 375-394:

```c
if (n_gen >= 6 && rt) {
    int look_back = (n_gen < 8) ? n_gen : 8;
    
    for (int i = 0; i < look_back; i++) {
        int ti = rt[n_total - 1 - i];
        if (ti < 0 || ti >= vocab_size) continue;
        
        // Count occurrences in look_back window
        int count = 0;
        for (int j = 0; j < look_back; j++) {
            if (rt[n_total - 1 - j] == ti) count++;
        }
        
        // If token appears more than once, hard-block
        if (count > 1) {
            logits_copy[ti] = -1e9f;
        }
    }
}
```

**Problem:** A token appearing exactly 2 times in the last 8 positions gets blocked entirely (`-1e9f`). This is binary behavior - no middle ground.

**Impact:** After 6+ tokens of generation:
- Tokens that naturally appear twice (e.g., "the the" or "I I") get blocked
- The model loses diversity even when repetition is semantically appropriate

**Evidence from trace:** With default CLI settings (rep_penalty=1.3), after 6 generations:
1. Hard block fires first (sets to -1e9f)
2. Soft penalty applied afterward (but already zeroed)
3. The binary blocking creates artificial constraints

### Issue 2.2: Soft Repetition Penalty Includes Prompt Tokens (MEDIUM Priority)

From `sm2_sampling.c` lines 396-407:

```c
if (effective_penalty > 1.0f && ctx) {
    int recent_count = ctx->scratch.kv_cache_len;
    if (recent_count > 0 && ctx->scratch.recent_tokens) {
        sm2_apply_repetition_penalty(logits_copy, vocab_size,
                                     ctx->scratch.recent_tokens,
                                     recent_count,
                                     effective_penalty);
    }
}
```

**Problem:** `kv_cache_len` includes both prompt tokens AND generated tokens. The soft penalty operates on the ENTIRE sequence history, not just recent generation.

**Inconsistency:** Hard block uses `n_gen = kv_cache_len - 2` (excludes prompt), but soft penalty uses `kv_cache_len` (includes prompt).

**Impact:** Common words from the prompt (like "the", "a", "to") get penalized throughout generation, reducing their probability even when appropriate.

### Issue 2.3: Temperature Inconsistency (MEDIUM Priority)

From documents 005 and 007:

- `sm2_sample_top_k` (line 268): skips temperature if `temp == 1.0f`
- `sm2_sample_top_p` (line 189): applies temperature for any `temp > 0.0f`

**Impact:**
- With `top_k=40, top_p=90, temp=0.7`: top-k path, temperature applied -> correct
- With `top_p=90, top_k=0, temp=0.7`: top-p path, temperature applied -> correct
- With `top_k=40, top_p=100, temp=0.7`: greedy path, NO temperature -> incorrect

The greedy fallback completely ignores temperature, which can produce overly deterministic output.

### The Garbled Output Mystery

From test runs:
```
# Run 1 (temp=0.7, top_p=90):
Output: 
***   ***     *******    #     *    127563498     #     MacGee, Charle

# Run 2 (temp=0, greedy):
Output: . Here are some more detail:
```

**Hypothesis:** The garbled "*** ***" output is what the model ACTUALLY produces when logits are distorted by numerical precision errors. The model is producing tokens, but the token IDs map to ASCII symbols that look garbled.

**Why this happens:**
1. The fast matmul path (4x unrolled) does NOT use Kahan summation
2. 49152 output logits, each summing 576 products = ~28M float operations
3. Without Kahan compensation, accumulated rounding error can flip the argmax
4. The "garbled" tokens (like "***") are valid tokens that decode to those characters

## Section 4: Numerical Precision Analysis

### Issue 4.1: Fast Matmul Lacks Kahan Summation (CRITICAL)

From `sm2_matmul_fast.c`:
```c
float sum0 = 0.0f, sum1 = 0.0f, sum2 = 0.0f, sum3 = 0.0f;
for (; l + 3 < k; l += 4) {
    sum0 += a_row[l] * f16_to_f32(w0);
    // ...
}
out[i * n + j] = sum0 + sum1 + sum2 + sum3;
```

**Contrast with context code (Kahan summation):**
```c
for (int j = 0; j < dim; j++) {
    float w = sm2_f16_to_float(model->q_proj[q_off + i * dim + j]);
    float y = xb_out[j] * w - c;  // compensate
    float t = sum + y;
    c = (t - sum) - y;
    sum = t;
}
```

**Impact on quality:**
- Logits matmul: 49152 outputs x 576 additions each = ~28M FP32 operations
- Without Kahan: error can accumulate to ~1e-6 per operation
- For 576 additions: potential error ~576 * 1e-6 = 5.76e-4
- Logit range is ~21 (27.6 - 6.0), error ~0.0006 is small
- BUT: F16 dequantization error compounds (10-bit mantissa ~3 decimal digits)

**Verdict:** The context code uses Kahan for all projections. If the fast backend is used for logits, precision degrades.

### Issue 4.2: F16 Dequantization Error Propagation

```c
float w = sm2_f16_to_float(model->q_proj[q_off + i * dim + j]);
float y = xb_out[j] * w - c;
```

- F16 has 10-bit mantissa (~3 decimal digits precision)
- `xb_out[j]` is FP32 (~7 decimal digits)
- Product `xb_out[j] * w` compounds quantization error
- After 576 such products, error can flip relative ordering of logits

## Section 5: Actionable Fixes

### Priority 1: CRITICAL

#### Fix 1.1: Add Kahan Summation to Fast Matmul Path

**File:** `src/sm2_matmul_fast.c`
**Lines:** ~100-120 (the inner accumulation loop)

**Current code:**
```c
float sum0 = 0.0f, sum1 = 0.0f, sum2 = 0.0f, sum3 = 0.0f;
for (; l + 3 < k; l += 4) {
    sum0 += a_row[l] * f16_to_f32(w0);
    // ...
}
out[i * n + j] = sum0 + sum1 + sum2 + sum3;
```

**Fix:**
```c
float sum0 = 0.0f, c0 = 0.0f;
float sum1 = 0.0f, c1 = 0.0f;
float sum2 = 0.0f, c2 = 0.0f;
float sum3 = 0.0f, c3 = 0.0f;
for (; l + 3 < k; l += 4) {
    float w0 = f16_to_f32(w0_raw);
    float y0 = a_row[l] * w0 - c0;
    float t0 = sum0 + y0;
    c0 = (t0 - sum0) - y0;
    sum0 = t0;
    // ... same for sum1, sum2, sum3
}
float comp = (c0 + c1) + (c2 + c3);
out[i * n + j] = sum0 + sum1 + sum2 + sum3 + comp;
```

**Why it matters:** The logits matmul determines token selection. Without Kahan, accumulated error can cause wrong token to be selected, producing garbled output.

### Priority 2: HIGH

#### Fix 2.1: Relax Hard Block Threshold

**File:** `src/sm2_sampling.c`
**Lines:** 375-394

**Current behavior:** Any token appearing 2+ times in last 8 gets blocked to `-1e9f`.

**Problem:** Too aggressive for natural language. A token appearing twice in 8 tokens is not necessarily repetitive.

**Fix:**
```c
// Change from count > 1 to count > 2 (3+ occurrences)
if (count > 2) {
    logits_copy[ti] = -1e9f;
}
// OR: Scale down rather than hard block
if (count > 1) {
    logits_copy[ti] *= 0.5f;  // reduce but don't eliminate
}
```

**Why it matters:** The hard block creates binary behavior. Tokens that should have moderate probability get zeroed, reducing diversity and coherence.

#### Fix 2.2: Make Soft Penalty Use Consistent Token Window

**File:** `src/sm2_sampling.c`
**Lines:** 396-407

**Problem:** Soft penalty uses `kv_cache_len` (includes prompt), but hard block uses `n_gen = kv_cache_len - 2` (excludes prompt).

**Fix:**
```c
// Apply penalty only to generated tokens, not prompt
int gen_start = prefill_length;  // Store this during prefill
int gen_count = kv_cache_len - gen_start;
if (gen_count > 0) {
    sm2_apply_repetition_penalty(logits_copy, vocab_size,
                                 ctx->scratch.recent_tokens + gen_start,
                                 gen_count,
                                 effective_penalty);
}
```

**Why it matters:** Common words from the prompt ("the", "a", "to") get unfairly penalized throughout generation.

### Priority 3: MEDIUM

#### Fix 3.1: Add Temperature to Greedy Fallback

**File:** `src/sm2_sampling.c`
**Lines:** 418-429

**Current:**
```c
} else {
    // Greedy
    int max_idx = 0;
    float max_val = logits_copy[0];

```

**Fix:** Apply temperature before greedy fallback:
```c
} else {
    // Temperature still applies even in greedy mode
    if (params->temperature > 0.0f && params->temperature != 1.0f) {
        for (int i = 0; i < vocab_size; i++) {
            logits_copy[i] /= params->temperature;
        }
    }
    // Then greedy select
    int max_idx = 0;
    float max_val = logits_copy[0];
    // ...

```

**Why it matters:** `top_p=100` (or any value >= 100) triggers greedy mode, ignoring temperature entirely. This produces overly deterministic output.

**File:** `src/sm2_sampling.c`
**Lines:** 268 (top_k), 189 (top_p)

**Fix:** Make both paths apply temperature for `temp > 0` (not `temp != 1.0`):
```c
// In sm2_sample_top_k:
if (temp > 0.0f) {  // Changed from temp != 1.0f
```

## Section 6: Root Cause Summary

### Primary Root Cause: Numerical Precision Degradation

**Evidence:**
1. `check_layer_trace` shows valid logits distribution (top 27.59, range 21)
2. But test runs produce garbled output "*** ***"
3. Fast matmul lacks Kahan summation
4. F16 dequantization compounds error

**Mechanism:**
- 49152 logits, each 576 FP32 operations
- Without Kahan, rounding error accumulates
- Error can flip argmax, selecting wrong token
- Wrong tokens decode to garbled output

### Secondary Root Cause: Overly Aggressive Repetition Penalty

**Evidence:**
1. Hard block fires after 6 tokens (count > 1)
2. Binary blocking creates artificial constraints
3. Soft penalty includes prompt tokens

**Mechanism:**
- Tokens appearing 2+ times get zeroed to `-1e9f`
- Common words from prompt get penalized
- Reduces diversity and coherence

### Contributing Factor: Temperature Inconsistency

**Evidence:**
1. Top-k path: `temp != 1.0f` condition
2. Top-p path: `temp > 0.0f` condition
3. Greedy fallback ignores temperature
