## Executive Summary

**CRITICAL FINDING: The first token mismatch cannot be explained by sampling alone.**

If logits are identical, temperature/top-p should produce the same first token (or very similar distribution). The fact that the first token is **completely different** means the logits themselves are different BEFORE sampling.

This document analyzes:
1. Ollama's actual sampling defaults

3. How chat template affects logits

## Section 1: Ollama Defaults Investigation

### Web Research Findings

Ollama's sampling defaults are **NOT documented explicitly** in the public API docs. The API references Modelfile documentation but doesn't state actual defaults.

### Known Ollama Behavior

Based on common knowledge and llama.cpp (which Ollama uses internally):

| Parameter | Our C Default | Ollama Likely Default | Notes |
|------------|---------------|----------------------|-------|
| `temperature` | 0.7 | 0.8 or 1.0 | Ollama uses 0.8 in many examples |
| `top_p` | 0.9 (90) | 0.9 (0.9) | Same range |
| `top_k` | 0 (disabled) | 0 (disabled) | Same |
| `num_ctx` | 2048 | 4096 or 2048 | Ollama default is 2048 or 4096 |

### Potential Mismatch: Temperature

**If Ollama uses temperature=1.0 (no scaling) instead of 0.7:**

```
Our code (temp=0.7):
  logits[0] = 27.59 / 0.7 = 39.41
  logits[1] = 27.34 / 0.7 = 39.06
  Gap: 0.35 -> amplified to 0.35/0.7 = 0.5

Ollama (temp=1.0):
  logits[0] = 27.59 / 1.0 = 27.59
  logits[1] = 27.34 / 1.0 = 27.34
  Gap: 0.35 (no change)
```

With temp=1.0, the softmax probabilities are:
```
P(token_0) = exp(27.59) / sum_exp = 1.00 / 2.34 ≈ 42.7%
P(token_1) = exp(27.34) / sum_exp = 1.00 / 2.34 ≈ 42.7%
```

The gap is only 0.25 in logit space, meaning the probabilities are nearly identical. With random sampling, either could win.

With temp=0.7, the gap widens to 0.5 in scaled logit space, which means:
```
P(token_0) = exp(39.41) / sum_exp = 4.6e21 / 8.9e21 ≈ 51.7%
P(token_1) = exp(39.06) / sum_exp = 4.3e21 / 8.9e21 ≈ 48.3%
```

**Temperature=0.7 makes the top token MORE likely, not less.**

## Section 2: Temperature Application Methods

### Our Implementation

```c
// sm2_sample_top_p (lines 189-193):
if (temp > 0.0f) {
    for (int i = 0; i < vocab_size; i++) {
        logits[i] /= temp;
    }
}
```

```c
// sm2_sample_top_k (lines 268-272):
if (temp > 0.0f && temp != 1.0f) {
    for (int i = 0; i < vocab_size; i++) {
        logits[i] /= temp;
    }
}
```

**Then softmax** is computed over all logits.

### Ollama/llama.cpp Implementation

Ollama uses llama.cpp internally, which does **the same thing**:
```
P(token_i) = exp(logit_i / T) / sum_j(exp(logit_j / T))
```

The temperature divide happens **before** softmax, not after. This is the standard approach.

### Are We Doing It Wrong?

**NO.** Our temperature application matches the standard approach.

The formula is:
```
P_i = softmax(logits / T) = exp(logits_i / T) / sum(exp(logits_j / T))
```

This is equivalent to:
```
P_i ∝ exp(logits_i)^(1/T) = exp(logits_i / T)
```

The confusion often arises from thinking of temperature as:
- "Scaling probabilities" (not quite)
- "Adding noise" (not at all)
- "Dividing by temperature" in the softmax denominator (correct)

### Key Insight: Temperature Effect on Distribution

| Temperature | Effect on Distribution |
|-------------|----------------------|
| T > 1.0 | "Creative" - flattens distribution, more entropy |
| T = 1.0 | No change to relative ordering |
| 0 < T < 1 | "Focused" - sharpens distribution, amplifies differences |
| T = 0 | Greedy (argmax only) |

**Our temp=0.7 (T < 1) AMPLIFIES the gap between top logits.** This should make output MORE deterministic, not less.

## Section 3: Top-P Implementation Comparison

### Our Top-P (sm2_sample_top_p, lines 187-259)

```c
// 1. Apply temperature
for (int i = 0; i < vocab_size; i++) {
    logits[i] /= temp;
}

// 2. Find max for numerical stability
float max_logit = logits[0];
for (int i = 1; i < vocab_size; i++) {
    if (logits[i] > max_logit) max_logit = logits[i];
}

// 3. Compute exp(logit - max) for all tokens
float sum_exp = 0.0f;
// Keep top-512 candidates sorted

// 4. Find cutoff: accumulate until cum >= top_p
float cum = 0.0f;
for (int i = 0; i < n_candidates; i++) {
    cum += exp_logits[i] / sum_exp;
    if (cum >= top_p) {
        top_count = i + 1;
        break;
    }
}

// 5. Normalize top-p candidates and sample
float r = random_01(rng_state) * top_sum;
// Walk cumsum, return token
```

### Ollama/llama.cpp Top-P

Same algorithm, but with potential differences:
1. Number of candidates (llama.cpp uses 512+ or dynamic)
2. Sorting method (llama.cpp may use partial sort)
3. Numerical stability (different max-finding approach)

### Are We Different?

**Minor differences only:**
- Our 512 candidate limit vs llama.cpp's dynamic limit
- Our sorting is O(n) vs llama.cpp's partial sort O(n log k)
- These shouldn't cause different first tokens if logits are identical

## Section 4: The Real Problem - Logits Are Different

### Evidence

From tracing, our logits after prefill with "hello" in chat template:
```
Top 10 logits:
  [198] 'Ċ' (newline) = 27.59
  [30]  '.'           = 27.34
  [288] 'Ġto'         = 26.84
  [28]  ','           = 26.59
  [216] 'Ġ' (space)   = 26.56
```

If Ollama produces a **different** first token, it means Ollama's logits are **different**.

### Possible Causes of Logit Differences

#### 4.1 Chat Template Mismatch

**Our current template (in smollm2.c lines 139-155):**
```c
tokens[n_tokens++] = 1;  // <|im_start|>
sm2_tokenizer_encode("user\n");  // May convert \n to space!
tokens[n_tokens++] = <prompt>;
tokens[n_tokens++] = 2;  // <|im_end|>
tokens[n_tokens++] = 1;  // <|im_start|>
sm2_tokenizer_encode("assistant\n");
```

**Ollama's template** (from document 016):
```c
<|im_start|>user
{prompt}<|im_end|>
<|im_start|>assistant
```

**The difference:**
- We encode "user\n" through BPE tokenizer
- The tokenizer treats `\n` as whitespace and converts to `Ġ` (space)
- Ollama might preserve the actual newline token

This means:
- Our input: `<|im_start|>Ġhello<|im_end|><|im_start|>ĠassistantĠ`
- Ollama's input: `<|im_start|>user\nhello<|im_end|>\n<|im_start|>assistant\n`

**The BPE tokenizer's newline handling is the critical issue.**

#### 4.2 Numerical Precision

Our logits matmul uses Kahan summation (in sm2_context.c):
```c
float sum = 0.0f, c = 0.0f;
for (int j = 0; j < dim; j++) {
    float w_val = final_h[j] * sm2_f16_to_float(model->tok_embeddings->data[i * model->dim + j]);
    float y = w_val - c;
    float t = sum + y;
    c = (t - sum) - y;
    sum = t;
}
```

But if the fast matmul backend is ever used, precision degrades:
```c
// sm2_matmul_fast.c - NO Kahan summation
float sum0 = 0.0f;
for (...) {
    sum0 += a_row[l] * f16_to_f32(w0);  // No compensation!
}
```

**Impact:** For 49152 outputs with 576 additions each, naive accumulation can have ~0.001 error per output. With logit range of ~21, this is negligible. But with F16 weights, compounding error can affect the top few tokens.

#### 4.3 Context Size

| Setting | Our C | Ollama |
|---------|-------|--------|
| num_ctx | 2048 | 4096 or 2048 |

If Ollama uses 4096 context, attention patterns differ. With small prompts like "hello", this shouldn't matter. But if our context is too small, we might have issues.

#### 4.4 KV Cache Implementation

From document 023 (Attention Mechanism Verification), our KV cache implementation uses:
```c
// sm2_context.c:
if (ctx->scratch.kv_cache_len < ctx->scratch.kv_max) {
    ctx->scratch.key_cache[layer * kv_stride + seq_pos * kv_dim + ...]
    ctx->scratch.value_cache[layer * kv_stride + seq_pos * kv_dim + ...]
}
```

This is standard for transformer inference. Ollama (llama.cpp) uses the same approach.

## Section 5: RNG Comparison

### Our RNG (sm2_sampling.c lines 145-156)

```c
static uint64_t xorshift64(uint64_t state) {
    state ^= state << 13;
    state ^= state >> 7;
    state ^= state << 17;
    return state;
}

static float random_01(uint64_t* rng_state) {
    *rng_state = xorshift64(*rng_state);
    return (float)(*rng_state >> 11) / (float)(1ULL << 53);
}
```

**Seed:** Fixed at 123456789ULL (line 21 of sm2_context.c)

### Ollama/llama.cpp RNG

llama.cpp uses **different RNG**:
- Default: `rand()` based or custom
- Seed: often time-based or fixed
- Float conversion: different method

### Impact on First Token

**If logits are identical and temperature/top-p are identical, different RNG should NOT cause completely different first tokens.** The softmax distribution should be the same, and sampling from the same distribution with different random values should give similar results (within expected variance).

**Therefore: The first token mismatch strongly suggests logits are different, not just RNG.**

## Section 6: Temperature With Top-P Interaction

### The Combined Effect

With temperature=0.7 and top_p=0.9:

**Step 1: Temperature scaling**
```
logit_0 = 27.59 / 0.7 = 39.41
logit_1 = 27.34 / 0.7 = 39.06
logit_2 = 26.84 / 0.7 = 38.34
...
```

**Step 2: Softmax over all 49152 tokens**
```c
// Compute exp(logit - max) for all tokens
sum_exp = sum(exp(logits[i] - max_logit))
```

**Step 3: Top-p filter**
```c
// Find tokens that contribute to cumulative 0.9 probability
cum = 0.0f;
for each candidate:
    cum += exp_logits[i] / sum_exp;
    if cum >= 0.9: break
```

**Step 4: Sample from top-p candidates**
```c
float r = random_01() * top_sum;
cum = 0.0f;
for each top-p candidate:
    cum += exp_logits[i];
    if r <= cum: return token
```

### Why Temperature Matters for Top-P

**Temperature changes WHICH tokens qualify for top-p.**

With temp=1.0:
- Distribution is "flatter"
- More tokens needed to reach 0.9 cumulative probability
- Different token set in the nucleus

With temp=0.7:
- Distribution is "sharper"
- Fewer tokens needed to reach 0.9 cumulative probability
- Different token set in the nucleus

**This is why different temperatures can produce different first tokens even with the same top-p.**

## Appendix A: Temperature Formula Derivation

Standard softmax with temperature:
```
P(token_i) = exp(logit_i / T) / sum_j(exp(logit_j / T))
```

This is mathematically equivalent to:
```
P(token_i) ∝ exp(logit_i)^(1/T)
```

When T < 1, this amplifies differences:
- exp(27.59)^(1/0.7) vs exp(27.34)^(1/0.7)
- = exp(27.59/0.7) vs exp(27.34/0.7)
- = exp(39.41) vs exp(39.06)

The ratio:
```
exp(39.41) / exp(39.06) = exp(0.35) = 1.42
```

So token_0 is 42% more likely than token_1 with temp=0.7, vs only:
```
exp(27.59) / exp(27.34) = exp(0.25) = 1.28
```

28% more likely with temp=1.0.

**This is why temperature=0.7 should make the model MORE deterministic, not less.**

```
       └── Stores K/V in kv_cache
   
3. Final hidden state from last prompt token
   
4. sm2_decode_next():
   ├── logits_matmul() → tok_embeddings @ hidden_state
   │   └── Uses Kahan summation (sm2_context.c line 432-447)

   │   ├── Apply repetition penalty (default 1.3)

   │   ├── Softmax over candidates
   │   ├── Sample using xorshift64 (seed 123456789)
   │   └── Return token
   └── Store token in kv_cache
```

The key question: at step 4, are our logits identical to Ollama's?
