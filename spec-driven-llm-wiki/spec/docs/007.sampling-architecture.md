## 1. Logits Computation

### Token Embedding Lookup

The hidden state (a `dim`-dimensional float vector) is projected to vocabulary-size logits via a **transposed matmul** with the `tok_embeddings` weight matrix:

```
logits = tok_embeddings @ hidden_state.T
       = [vocab_size, dim] @ [dim]
       => [vocab_size]
```

In `sm2_context.c`, this happens in two places:

**Prefill** (`sm2_prefill`, lines 432-447):
```c
for (int i = 0; i < model->vocab_size; i++) {
    float sum = 0.0f;
    float c = 0.0f;
    for (int j = 0; j < model->dim; j++) {
        float w_val = final_h[j] * sm2_f16_to_float(model->tok_embeddings->data[i * model->dim + j]);
        float y = w_val - c;
        float t = sum + y;
        c = (t - sum) - y;
        sum = t;
    }
    ctx->scratch.logits[i] = sum;
}
```

**Decode** (`sm2_decode_next`, lines 491-505):
Identical pattern using `ctx->model->tok_embeddings`.

The weight matrix `tok_embeddings` is `[vocab_size=49152, dim]` of F16. The hidden state is `dim`-dimensional float. The inner loop over `dim` accumulates the dot product for each vocabulary entry.

### Where It Fits in the Forward Pass

The full decode flow is:

1. **Embedding lookup** (`embedding_lookup`) -- converts token ID to `dim`-dimensional vector via `tok_embeddings`
2. **N transformer layers** (`layer_forward`) -- each applies RMSNorm, Q/K/V projections (with Kahan summation), RoPE, attention, O projection, SwiGLU FFN
3. **Final RMSNorm** on the last hidden state
4. **Logits matmul** (`tok_embeddings @ hidden_state.T`) -- produces 49152 logits

## 2. Kahan Summation

### What It Is

Kahan summation (also called compensated summation) reduces floating-point rounding error in large summation loops. In naive summation, adding many small floats to a large accumulator loses precision. Kahan's algorithm maintains a running compensation term `c` that captures the lost low-order bits.

### The Algorithm

```c
float sum = 0.0f;
float c = 0.0f;  // compensation
for (int j = 0; j < dim; j++) {
    float w_val = hidden[j] * weight[j];  // F16 weight -> float, then multiply
    float y = w_val - c;                   // compensate previous error
    float t = sum + y;                     // new sum
    c = (t - sum) - y;                     // compute new compensation
    sum = t;
}
```

### Where It's Used

Kahan summation is used in **every matmul** inside `sm2_context.c`:

| Location | Matmul | Size |
|---|---|---|
| `layer_forward` L223-236 | Q projection | `[dim, dim]` |
| `layer_forward` L239-251 | K projection | `[kv_dim, dim]` |
| `layer_forward` L254-266 | V projection | `[kv_dim, dim]` |
| `layer_forward` L286-297 | O projection | `[dim, kv_dim]` |
| `layer_forward` L323-334 | gate_proj (SwiGLU) | `[hidden_dim, dim]` |
| `layer_forward` L338-349 | up_proj (SwiGLU) | `[hidden_dim, dim]` |
| `layer_forward` L361-373 | down_proj (SwiGLU) | `[dim, hidden_dim]` |
| `sm2_prefill` L435-446 | **tok_embeddings** (logits) | `[vocab_size, dim]` |
| `sm2_decode_next` L493-504 | **tok_embeddings** (logits) | `[vocab_size, dim]` |

For the logits matmul (49152 outputs, each summing `dim` elements), this is critical: with naive summation, the accumulated rounding error across 576 additions per output could distort the relative ordering of logits, especially for smaller `dim` models (576 for 135M). Without Kahan summation, the top-logit might not actually be the true max, causing incorrect token selection.

### Contrast with Fast Backend

`sm2_matmul_fast.c` uses **4x loop unrolling** but no Kahan summation:
```c
float sum0 = 0.0f, sum1 = 0.0f, sum2 = 0.0f, sum3 = 0.0f;
for (; l + 3 < k; l += 4) {
    sum0 += a_row[l] * f16_to_f32(w0);
    // ...
}
out[i * n + j] = sum0 + sum1 + sum2 + sum3;
```
This is faster but has higher numerical error. The context code uses Kahan for correctness; the fast backend sacrifices precision for speed.

## 3. Greedy Sampling (temp=0)

When `params->temperature == 0.0f` (or when neither top-k nor top-p is configured), greedy sampling selects the token with the **maximum logit value**:

```c
// sm2_sample_top_k path, temp==0 falls through
// sm2_sample_token fallback (lines 419-428):
int max_idx = 0;
float max_val = logits_copy[0];
for (int i = 1; i < vocab_size; i++) {
    if (logits_copy[i] > max_val) {
        max_val = logits_copy[i];
        max_idx = i;
    }
}
return max_idx;
```

**Key points:**
- No softmax, no probability distribution, no RNG -- just argmax
- The temperature division `logits[i] /= temp` is skipped when `temp <= 0` (both `sm2_sample_top_k` and `sm2_sample_top_p` use `if (temp > 0.0f)`)
- Greedy is deterministic given the same logits

## 4. Temperature Sampling (temp>0)

Temperature divides logits before the softmax, effectively reshaping the probability distribution:

```
P(token_i) = exp(logit_i / T) / sum(exp(logit_j / T))

where T = temperature
```

- **T > 1.0** ("creative" / "high temperature"): softens the distribution, increases entropy, more diverse/random output
- **T = 1.0** ("default"): no change to logits
- **0 < T < 1.0** ("focused" / "low temperature"): sharpens the distribution, concentrates probability on top tokens
- **T = 0.0**: greedy (argmax), handled separately

### Implementation in Top-K Path

```c
// sm2_sample_top_k (lines 268-272):
if (temp > 0.0f) {
    for (int i = 0; i < vocab_size; i++) {
        logits[i] /= temp;
    }
}
```

### Implementation in Top-P Path

```c
// sm2_sample_top_p (lines 189-193):
if (temp > 0.0f) {
    for (int i = 0; i < vocab_size; i++) {
        logits[i] /= temp;
    }
}
```

Both functions apply temperature for any `temp > 0.0f`. There is no `temp == 1.0f` shortcut -- the division is always performed when temperature is positive.

## 5. Top-K Sampling

Top-K filters the distribution to the **K most likely tokens**, then samples from the normalized softmax over those K tokens.

### Algorithm (in `sm2_sample_top_k`)

1. **Apply temperature**: `logits[i] /= temp` (if temp > 0.0f)
2. **Find max logit**: for numerical stability in softmax
3. **Partial selection**: scan all vocab_size tokens, maintain sorted top-K using insertion sort + bubble-up. Complexity O(vocab_size * log(K)) but with small constant.
4. **Normalize**: compute `sum_exp` of the K exp(logit) values
5. **Sample**: draw `r = random() * sum_exp`, walk cumsum until `r <= cumsum`, return that token

```c
// Partial selection (lines 289-332):
for (int i = 0; i < vocab_size; i++) {
    float e = expf(logits[i] - max_logit);
    if (n_selected < top_k) {
        // fill
    } else if (e > exp_vals[top_k - 1]) {
        // replace smallest, bubble up
    }
}

// Sample (lines 341-348):
float r = random_01(rng_state) * sum_exp;
float cum = 0.0f;
for (int i = 0; i < top_k; i++) {
    cum += exp_vals[i];
    if (r <= cum) return indices[i];
}
return indices[0];  // fallback
```

### Key Parameters

- `top_k <= 0 || top_k > 256`: clamped to 256
- `top_k > vocab_size`: clamped to `vocab_size`
- Default CLI: `top_k = 0` (disabled)

## 6. Top-P (Nucleus) Sampling

Top-P dynamically selects the smallest subset of tokens whose cumulative probability mass meets or exceeds `top_p`.

### Algorithm (in `sm2_sample_top_p`)

1. **Apply temperature**: divide all logits by temperature
2. **Find max logit**: for numerical stability
3. **First pass**: compute `exp(logit_i - max)` for all tokens, maintain sorted top-512 candidates
4. **Find cutoff**: accumulate `cum += exp_logits[i] / sum_exp` until `cum >= top_p`, set `top_count`
5. **Normalize**: sum only the top-p candidates (`top_sum`)
6. **Sample**: draw random, walk cumulative sum over top-p candidates

```c
// Find cutoff (lines 232-240):
float cum = 0.0f;
int top_count = n_candidates;
for (int i = 0; i < n_candidates; i++) {
    cum += exp_logits[i] / sum_exp;
    if (cum >= top_p) {
        top_count = i + 1;
        break;
    }
}
```

The top-p value from CLI is an **integer 0-100**, converted to float `[0.0, 1.0]`:
```c
float top_p_val = params->top_p / 100.0f;
```

### Top-512 Candidate Limit

The code limits to 512 candidates to avoid sorting all 49152 logits:
```c
float exp_logits[512];
int indices[512];
```

This is a quality/performance tradeoff. If `top_p = 0.95` but the true 500th-600th tokens collectively hold the missing probability mass, they will be missed. For `top_p = 0.9-0.95` this is rarely an issue.

### Default CLI: `top_p = 90` (0.90)

## 7. Repetition Penalty

### How It's Tracked

A **ring buffer** (`recent_tokens`) tracks all generated token IDs. It's a flat `int` array of size `max_seq` (8192), with tokens written sequentially:

```c
// sm2_create_context (line 75):
ctx->scratch.recent_tokens = calloc(max_seq, sizeof(int));

// sm2_prefill (line 415-417):
if (ctx->scratch.recent_tokens && t < ctx->scratch.recent_max) {
    ctx->scratch.recent_tokens[t] = tokens[t];
}

// sm2_decode_next (line 511-513):
if (ctx->scratch.recent_tokens && ctx->scratch.kv_cache_len < ctx->scratch.recent_max) {
    ctx->scratch.recent_tokens[ctx->scratch.kv_cache_len] = token;
}
```

The buffer index is `kv_cache_len` (the number of tokens currently in the KV cache), which starts at the prompt length after prefill and increments by 1 each decode step.

**Important**: `kv_cache_len` is **inclusive** of the current position. After prefill of N tokens, `kv_cache_len = N`. During decode step at position N, the newly generated token at position N is tracked at index `kv_cache_len = N`.

### How It's Applied

**Method: Divide** (penalty > 1.0f)

```c
// sm2_apply_repetition_penalty (lines 122-139):
for (int i = 0; i < n_recent; i++) {
    int token_id = recent_tokens[i];
    if (token_id >= 0 && token_id < vocab_size) {
        if (logits[token_id] > 0) {
            logits[token_id] /= penalty;    // positive logits: reduce probability
        } else {
            logits[token_id] *= penalty;    // negative logits: increase (make more negative)
        }
    }
}
```

**Logic**: For positive logits, dividing by penalty `1.3` makes them smaller. For negative logits, multiplying by penalty `1.3` makes them more negative. This pushes repeated tokens DOWN in the ranking regardless of their sign. The sign-aware version is the HuggingFace/llama.c approach.

### Additional Hard Blocking in `sm2_sample_token`

Before calling the sampling functions, `sm2_sample_token` has a **secondary repetition detector** with two tiers:

```c
// sm2_sample_token (lines 375-405):
if (n_gen >= 6 && rt) {
    int look_back = (n_gen < 8) ? n_gen : 8;
    for (int i = 0; i < look_back; i++) {
        int ti = rt[n_total - 1 - i];
        // Count occurrences in look_back window (generated tokens only)
        int count = 0;
        for (int j = 0; j < look_back; j++) {
            int idx = n_total - 1 - j;
            if (idx >= gen_start && rt[idx] == ti) count++;
        }
        if (count > 2) {
            logits_copy[ti] = -1e9f;       // HARD BLOCK: 3+ occurrences
        } else if (count > 1) {
            logits_copy[ti] *= 0.5f;        // SCALE DOWN: 2-3 occurrences
        }
    }
}
```

This looks at the **last 8 generated tokens** (fewer during early generation), counts occurrences within the generated portion only (excluding prompt tokens), and applies two tiers:
- **3+ occurrences**: hard block to `-1e9f` (zero probability)
- **2 occurrences**: scale down to 50% (soft reduction, not elimination)

This is less aggressive than a pure `count > 1` hard block, preserving some probability for tokens that only repeat twice.

### Default Values

| Parameter | Context Default | CLI Default |
|---|---|---|
| `repetition_penalty` | `1.0f` (disabled) | `1.3f` |
| `penalty_window` | `100` | `32` |

Note the discrepancy: `sm2_create_context` sets `penalty_window = 100`, but the CLI (`run_inference`) sets it to `32`. The `penalty_window` field itself is **never read** by `sm2_apply_repetition_penalty` -- the function uses `n_recent` (passed from caller) instead.

### Interaction with Sampling Modes

Repetition penalty is applied **before** sampling function dispatch:
```c
// sm2_sample_token lines 357-429:
// 1. Copy logits
// 2. Hard-block repeated tokens (set to -1e9f)
// 3. Apply sm2_apply_repetition_penalty (soft divide/multiply)
// 4. Dispatch to sm2_sample_top_k or sm2_sample_top_p or greedy
```

## 8. xorshift64 RNG

### Algorithm

```c
// sm2_sampling.c lines 145-156:
static uint64_t xorshift64(uint64_t state) {
    state ^= state << 13;
    state ^= state >> 7;
    state ^= state << 17;
    return state;
}

static float random_01(uint64_t* rng_state) {
    *rng_state = xorshift64(*rng_state);
    return (float)(*rng_state >> 11) / (float)(1ULL << 53);
}
```

### Seed Value

```c
// sm2_context.c line 21:
ctx->rng_state = 123456789ULL;
```

Fixed seed. Every run produces identical token sequences if all other factors (prompt, params) are identical. This is deterministic by design.

### Float Conversion: [0, 1)

```
rng_state (64-bit) >> 11  =>  53 low bits kept
Divide by 2^53            =>  uniform float in [0, 1)
```

The top 11 bits are discarded. This gives a 53-bit precision float in `[0, 1)`. The range is `[0, (2^53-1)/2^53)` = `[0, 0.9999999999999999...)`, so `1.0` is never returned.

### Period

xorshift64 has a period of `2^64 - 1` (full period for non-zero seed). With `123456789ULL` (non-zero), all 64 bits cycle before repeating.

### Quality Notes

- xorshift64 is fast but **not cryptographically secure** (trivial to predict)
- It has known statistical weaknesses (fails some TestU01 suites)
- For a 135M model at 10 tokens/second, you'd need ~58 million years to cycle through the full period
- The fixed seed is fine for inference determinism

## 9. Entropy Calculation

### Purpose

`compute_logits_entropy_fast` computes a normalized entropy measure from the logits distribution, returning a value in `[0, 1]` where 0 means the model is highly confident (distribution peaked on one token) and 1 means maximum entropy (uniform distribution across candidates).

### Algorithm

```c
// sm2_sampling.c lines 14-81:
static float compute_logits_entropy_fast(const float* logits, int vocab_size) {
    // 1. Find max logit for numerical stability
    float max_logit = logits[0];
    for (int i = 1; i < vocab_size; i++) {
        if (logits[i] > max_logit) max_logit = logits[i];
    }

    // 2. Partial selection: scan all vocab_size, keep top-64 sorted
    //    (avoids sorting all 49152 elements)
    int n_top = vocab_size > 64 ? 64 : vocab_size;
    float exp_vals[64];
    int indices[64];
    int n_found = 0;

    for (int i = 0; i < vocab_size; i++) {
        float exp_val = expf(logits[i] - max_logit);
        // Maintain sorted top-64 via insertion sort + bubble-up
        if (n_found < n_top) {
            indices[n_found] = i;
            exp_vals[n_found] = exp_val;
            n_found++;
            // Keep sorted descending
            for (int j = n_found - 1; j > 0 && exp_vals[j] > exp_vals[j-1]; j--) { ... }
        } else if (exp_val > exp_vals[n_top - 1]) {
            // Replace smallest, bubble up
            ...
        }
    }

    // 3. Compute probability distribution over top-64:
    float prob_sum = sum(exp_vals[0..n_found])
    float entropy = -sum(p_i * log(p_i)) for each candidate

    // 4. Normalize: H / log(64) = H / 4.1589
    return entropy / 4.16f;
}
```

### Design Rationale

- **Top-64 sampling**: Computing entropy over all 49152 tokens is expensive. Using top-64 captures the meaningful probability mass while keeping the computation fast.
- **Max entropy normalization (4.16)**: The maximum entropy for a 64-outcome uniform distribution is `log(64) = 4.1589`. Dividing by this normalizes output to `[0, 1]`.
- **Numerical stability**: Subtracting max logit before exp prevents overflow. Small probabilities (`p < 1e-10`) are skipped in the entropy sum to avoid log(0).

### Usage Context

This function is defined as `static` in `sm2_sampling.c` and is currently **not called** by `sm2_sample_token` or any other exported function. It appears to be a diagnostic/utility function for measuring model confidence, possibly intended for future adaptive sampling or quality monitoring features.

## 10. N-Gram Repetition Detection

### Purpose

`detect_ngram_repetition` scans recent tokens to detect immediate consecutive repetition patterns (e.g., "II II" where the same token appears twice in a row). It returns a repetition count as a signal of looping behavior.

```c
// sm2_sampling.c lines 88-115:
static int detect_ngram_repetition(const int* recent_tokens, int n_recent) {
    if (n_recent < 6) return 0;
    int max_check = n_recent > 16 ? 16 : n_recent;
    int rep_count = 0;

    // Check consecutive token pairs in recent_tokens:
    // tokens[n-1] == tokens[n-2], tokens[n-2] == tokens[n-3], etc.
    // Each consecutive equal pair increments rep_count
    for (int i = 0; i < max_check - 1; i++) {
        if (recent_tokens[n_recent - 1 - i] == recent_tokens[n_recent - 2 - i]) {
            rep_count++;
        }
    }
    return rep_count;
}
```

### Algorithm

- Scans the last **16 tokens** (or fewer if sequence is shorter)
- Counts consecutive identical pairs: each position where `tokens[i] == tokens[i-1]` adds 1 to rep_count
- Example: tokens ending in `[A, B, B, B, C]` gives `rep_count = 2` (two consecutive B pairs)
- Minimum `n_recent = 6` required before returning any count

### Usage Context

This function is also `static` and **not called** by `sm2_sample_token` or other exported functions. It coexists with the hard-block/scale-down repetition logic in `sm2_sample_token`, suggesting it may be a diagnostic tool or a candidate for future integration into the sampling pipeline.

```
        │
        ├── [1] memcpy(logits_copy, logits, 49152 * sizeof(float))

        │               count occurrences in window (generated portion only)

        │               elif count > 1: logits_copy[ti] *= 0.5f     // SCALE DOWN
        │
        ├── [4] if (repetition_penalty > 1.0 && recent_tokens):
        │           sm2_apply_repetition_penalty(

        │

        │   top_p_val = params->top_p / 100.0f
        │
        │   if (top_k > 0 && top_p_val < 1.0):
        │       return sm2_sample_top_k(logits_copy, 49152, top_k, temp, rng)
        │
        │   elif (top_p_val < 1.0):
        │       return sm2_sample_top_p(logits_copy, 49152, top_p_val, temp, rng)
        │
        │   elif (top_k > 0):
        │       return sm2_sample_top_k(logits_copy, 49152, top_k, temp, rng)
        │
        │   else:  // Greedy
        │       return argmax(logits_copy)  // no RNG call
        │
        ├── sm2_sample_top_k():
        │     ├── temp /= temp (if temp > 0.0f)
        │     ├── max_logit = max(logits)
        │     ├── partial selection: find top-K (max 256)
        │     ├── sum_exp = sum(exp(logit_i - max_logit)) for i in top-K
        │     ├── r = random_01() * sum_exp
        │     ├── cum = 0; walk cumsum; return index at cum >= r
        │     └── uses xorshift64 for RNG
        │
        └── sm2_sample_top_p():
              ├── temp /= temp (if temp > 0.0)
              ├── max_logit = max(logits)
              ├── first pass: compute all exp, keep top-512 sorted
              ├── sum_exp = sum(all exp)
              ├── cum = 0; accumulate until cum >= top_p; top_count = i+1
              ├── top_sum = sum(exp of top_count tokens)
              ├── r = random_01() * top_sum
              ├── cum = 0; walk cumsum over top_count; return index
              └── uses xorshift64 for RNG

sm2_decode_next() continued:
  ├── ctx->scratch.recent_tokens[kv_cache_len] = token  // track token
  ├── ctx->kv_cache_len++
  ├── ctx->last_token = token
  └── *out_token = token
```

### Data Flow: Logits to Token

```
Raw logits (49152 floats)
    │
    ├─ Hard block: tokens with count>2 in last 8 => -1e9f
    ├─ Scale down: tokens with count>1 in last 8 => *= 0.5f
    │
    ├─ Soft penalty: divide/multiply by rep_penalty for recent tokens
    │
    ├─ Temperature: logits /= temp (if temp > 0)
    │
    ├─ Softmax: exp(logit - max_logit) / sum_exp
    │
    ├─ Filter: top-K or top-p cutoff
    │
    ├─ Normalize: sum filtered exp values
    │
    ├─ Random: r = xorshift64() >> 11 / 2^53
    │
    └─ Cumulative sum walk: return token where cumsum >= r
```

## 13. Poor Output Quality: Root Causes

### A. Numerical Precision Issues

**Symptom**: Wrong tokens selected, especially during long generation.

**Root causes**:
1. **Naive summation in fast matmul** (`sm2_matmul_fast.c`): The fast 4x-unrolled accumulation without Kahan summation loses precision. For a 135M model with `dim=576`, each of 49152 output logits is the sum of 576 products. Float32 has ~7 decimal digits; 576 additions of random-magnitude values can accumulate error on the order of the logit magnitude itself. This can flip the argmax.

2. **F16 weight dequantization**: `f16_to_f32` has only 10 bits of mantissa (~3 decimal digits of precision). Multiplying two F16-converted values compounds quantization error inside the summation loop.

**Fix**: The context code uses Kahan summation for all projections, which mitigates this. But if the fast backend is ever used for the logits matmul, errors will increase.

### B. Repetition Penalty Problems

**Symptom**: Model stuck in loops ("IIIIII" or "the the the"), or alternates between 2-3 tokens.

**Root causes**:

1. **Overlapping hard block and soft penalty**: The hard block (`count > 2` in last 8 tokens sets logit to `-1e9f`) fires **before** the soft penalty. If a token appears 4+ times, the hard block has already zeroed it, making the soft penalty moot. The two-tier system (count>2 hard block, count>1 scale-down at 50%) reduces the binary nature of the interaction, but both layers still apply to the same tokens.

2. **`kv_cache_len` timing mismatch**: After `sm2_decode_next` calls `sm2_sample_token`, it then stores the token:
   ```c
   // Line 511-513
   ctx->scratch.recent_tokens[ctx->scratch.kv_cache_len] = token;
   ctx->scratch.kv_cache_len = seq_pos + 1;
   ```
   But inside `sm2_sample_token`, `kv_cache_len` hasn't been incremented yet (it's the pre-increment value). The repetition penalty operates on `kv_cache_len` tokens (the old count), but the hard block `look_back` uses `n_total - 1 - i` which is also pre-increment. This timing is correct -- but during prefill, `recent_tokens` is filled sequentially (line 416), and `kv_cache_len` tracks it. The problem: the hard block in `sm2_sample_token` only activates when `n_gen >= 6`, but early tokens (prompt + first 2-3 generations) are NOT penalized at all. Once `n_gen >= 6`, the hard block kicks in suddenly, potentially disrupting coherent early generation.

3. **`penalty_window` never read**: The field `penalty_window = 32` is set but the function `sm2_apply_repetition_penalty` receives `recent_count` from `kv_cache_len` directly, ignoring the window. This means the **entire sequence history** is penalized, not just the last 32 tokens. For long conversations, this accumulates penalty on all previously-seen words, potentially suppressing common words entirely.

4. **Penalty on prompt tokens**: `n_gen = kv_cache_len - 2` (line 373) excludes the prompt from repetition tracking. But the soft penalty at line 400 uses `kv_cache_len` directly. The discrepancy means soft penalty covers `kv_cache_len` tokens (prompt included) while hard block covers `n_gen` tokens (prompt excluded).

### C. Top-P / Top-K Interaction

**Symptom**: Very repetitive or very random output, depending on settings.

**Root causes**:

1. **Top-K and Top-P both enabled**: When `top_k > 0 && top_p < 1.0`, only `sm2_sample_top_k` is called. `top_p` is ignored in this branch. This is intentional (top-k takes priority), but may surprise users who set both.

2. **Top-512 candidate limit in top-p**: If the model distribution is very flat (many tokens with similar low probability), the true tokens needed to reach `top_p=0.9` might be beyond the 512th. The missing probability mass means the truncated distribution doesn't sum to `top_p`, and sampling is biased toward the top-512. This can manifest as reduced diversity.

### D. Temperature Inconsistency

**Symptom**: Temperature seems to have no effect, or excessive randomness.

**Root cause**: Both `sm2_sample_top_k` and `sm2_sample_top_p` now consistently apply temperature for any `temp > 0.0f`. However, the greedy fallback path (no top-k, top_p=100) completely ignores temperature:
- `top_k=40, top_p=90, temp=0.7`: top-k is used, temperature is applied -> correct
- `top_p=90, top_k=0, temp=0.7`: top-p is used, temperature is applied -> correct
- `top_k=40, top_p=100, temp=0.7`: greedy path is used (no temperature) -> temperature ignored

### E. Embedding / Logits Mismatch

**Symptom**: Model produces semantically incoherent text.

**Root cause**: The `tok_embeddings` weight matrix is used for **both** embedding lookup (input) and logits projection (output). The model uses tied weights (`tie_word_embeddings=True`). If the loaded model has incorrect or corrupted `tok_embeddings`, both directions are equally affected, but the effect on logits (only 1 matmul per decode step) is the most critical for sampling quality.

### F. Tokenizer Mismatch

**Symptom**: Garbled output, weird characters, or truncated generation.

**Root cause**: The BPE tokenizer maps bytes to token IDs. If the `byte_to_token` mapping is incorrect, input tokenization produces wrong IDs, which cascades to wrong embeddings to wrong logits. The CLI has fallback byte tokenization (lines 148-157 in `smollm2.c`) that kicks in if the proper BPE tokenizer fails to load.

### G. RoPE Position Encoding Bug

**Symptom**: Model output degrades over long sequences, attention doesn't see earlier context.

**Root cause**: If `kv_cache_len` is incorrect or the KV cache isn't properly indexed, attention scores won't match up positions, degrading long-range coherence.

---

## Summary

The sampling architecture chains: **hidden state -> logits matmul (Kahan) -> repetition handling -> temperature -> top-k/top-p filter -> softmax-normalize -> RNG sample -> token**. The critical paths are:

1. Kahan summation in logits matmul prevents numerical argmax errors
2. Repetition penalty has two layers: hard block (immediate repetition) + soft penalty (frequency-based)
3. CLI defaults (temp=0.7, top_p=90, rep_penalty=1.3) provide reasonable quality out of the box
4. The xorshift64 RNG with fixed seed 123456789ULL is deterministic

The most likely causes of poor output quality are: (1) float precision loss in the fast matmul path if used for logits, (2) the hard block / soft penalty interaction creating binary repetition behavior, (3) temperature being ignored in greedy mode, and (4) incorrect tokenizer loading causing bad tokenization. Additionally, the unreferenced `compute_logits_entropy_fast` and `detect_ngram_repetition` functions suggest diagnostic code that could be hooked into the sampling pipeline for adaptive quality control.
